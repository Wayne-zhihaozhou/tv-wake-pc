# 亮度 / 音量定时调节：探索记录

> 记录时间：2026-10-18（初探）／ 2026-10-19（亮度权限结论纠正）｜ 电视：LG OLED55G6PCA（G6，webOS 26 中国版，开发者模式）｜ 电视 IP：192.168.1.4:9922
> 目标：让电视在指定时间段自动切换屏幕亮度与音响音量（如 08:00–17:00 亮度 60、其他时段 40；09:00–22:00 音量 13、其他时段 7）。
>
> **⚠️ 最终结果（2026-10-19）**：**音量调度已实现并生效；亮度调度已取消**——
> 因为实机证明第三方 app 无法写 OLED 亮度（详见 §4.3）。代码中已移除全部亮度相关逻辑。
> 本文档保留了完整的探索过程与结论，供后人参考、避免重复踩坑。

## 2. 官方文档能查到什么

结论：**官方公开文档不支持这个需求**，必须实机探测内部 API。

| 需求 | 官方文档情况 |
|---|---|
| 音量 | `com.webos.audio` 公开的只有 `setMuted` / `volumeDown` / `volumeUp`（步进 +1/-1），**没有** `setVolume`（直接设具体值）。见 `docs/官方文档/03-API参考/媒体与数据/Audio音频.md` |
| 亮度 | **完全没有**。`com.webos.settingsservice/getSystemSettings` 只能读，且公开键里没有亮度；没有 `setScreenBrightness` 之类的公开接口 |

## 3. 实机探测方法

沿用 `电视SSH调试指南.md` 的 SSH 直连方式。两点实测变化：

1. **源地址会变**：文档里写的是 `192.168.1.6`，实际本次本机网卡 IP 已变为 `192.168.1.5`。直接用 `-b 192.168.1.6` 会报 `bind 192.168.1.6: Unknown error`。正确做法是先查本机同网段 IP（`Get-NetIPAddress`），再用它作 `-b`。
2. **路由被 VPN 劫持**：`Find-NetRoute -RemoteIPAddress 192.168.1.4` 显示走的是公司 VPN 网卡（172.16.1.x）。因此 `-b <本地物理网卡IP>` 绑定源地址是必需的，否则连不上。

可用的一行连接（口令 `C30E73` 走 `SSH_ASKPASS`，临时 `known_hosts` 规避 host key 漂移）：

```powershell
$ask = Join-Path $env:TEMP "wol-askpass.cmd"
Set-Content -Path $ask -Value "@echo C30E73" -Encoding ASCII
$env:SSH_ASKPASS = $ask
$env:SSH_ASKPASS_REQUIRE = 'force'
$env:DISPLAY = 'localhost:0'
$kh = Join-Path $env:TEMP "wol-known-hosts"
New-Item -ItemType File -Force $kh | Out-Null

ssh -b 192.168.1.5 -i "$env:USERPROFILE\.ssh\lg_webos" -p 9922 `
    -o StrictHostKeyChecking=no -o UserKnownHostsFile=$kh -o ConnectTimeout=8 `
    prisoner@192.168.1.4 "id; uname -a"

Remove-Item $ask -Force
```

在电视上跑 luna 调用统一用 `/usr/bin/luna-send-pub`（`prisoner` 无权用 `/usr/bin/luna-send`），且**必须加 `< /dev/null`**。

## 4. 核心发现

### 4.1 音量：实测完全可用 ✅

服务 URI `luna://com.webos.audio`，两个内部方法**公开可用**（不在官方文档里）：

```sh
# 读当前音量
luna-send-pub -n 1 -f luna://com.webos.audio/getVolume '{}' < /dev/null
# 实测返回
{ "returnValue": true, "muteStatus": false, "volume": 8, "scenario": "mastervolume_tv_speaker_ext" }

# 设置音量到 13
luna-send-pub -n 1 -f luna://com.webos.audio/setVolume '{"volume":13}' < /dev/null
# 实测返回
{ "returnValue": true }
```

> 注意：`getVolume` / `setVolume` **不在** `docs/官方文档/03-API参考/媒体与数据/Audio音频.md` 里，是实机探测发现的内部方法。
> 参数名是 `volume`（数值），非 `value` / `level`。

### 4.2 亮度：接口存在，但权限被锁（初探以为需 `settings` ACG）

> 注意：本节是最初的判断。**下一节 §4.3 已用实机否定**——声明 `settings` 也没用。保留本节是为了记录探索过程。

亮度走 `com.webos.settingsservice` 的 `picture` 类别：

```sh
luna-send-pub -n 1 -f luna://com.webos.settingsservice/setSystemSettings \
  '{"category":"picture","settings":{"backlight":60}}' < /dev/null
```

**实测（prisoner 身份）返回**：

```json
{ "returnValue": false, "errorText": "Access denied", "method": "setSystemSettings" }
```

读也是同理：`getSystemSettings` 指定 `picture` 类别同样返回 `Access denied`；不指定类别（如 `localeInfo`）则正常可读。

原因：**prisoner 身份没有 `settings` 权限**。而关键证据是——

`/usr/share/luna-service2/api-permissions.d/com.webos.settingsservice.api.json` 中，
`com.webos.settingsservice/setSystemSettings`、`getSystemSettings`、`setSystemSettingsPriv` 等
全部归入 **`settings` 组**；`settings` 组的定义（`groups.d/all.groups.json`）为：

```json
"settings": { "description": "Read and modify system preferences and settings", "public": true }
```

### 4.3 ⚠️ 结论（已实机纠正）：第三方 app 无法写亮度

**最初误判**：以为 `settings` 组 `public: true` 就能在 `appinfo.json` 里声明并用。
**实机验证推翻**：在 `appinfo.json` 的 `requiredACG` 里声明 `settings`（甚至 `settings.operation`）后，
app 调用 `setSystemSettings` 仍返回：

```json
{ "errorCode": -1, "returnValue": false, "errorText": "Denied method call \"setSystemSettings\" for category \"/\"" }
```

**根因**：webOS 26 中国版 ACG 机制中，**第三方 app 只有声明 `groups.d/public.groups.json` 里的组才真正生效**。
我列出了该文件全部 35 个公共组，结论：

- 没有任何「写设置 / 写亮度」的公共组；
- `settings` 组在 `all.groups.json`（系统级/特权组集合），app 声明不生效；
- `settings.operation` 在 `partner.groups.json`，`trust: partner`，需要 **partner 签名**，普通开发者模式 app 拿不到；
- 公共组里与显示相关的只有 `displaypanel.query`（只读 getPanelResolution）与 `videooutput.operation`（只管显示窗口，不涉及亮度）。

**因此：第三方普通 app 无法通过 ACG 写入 OLED 亮度。** 这是 LG 的安全限制。
若确实需要「定时调亮度」，必须走 **root / Homebrew Channel**（root 后可直接调 settingsservice 或更高权限服务），
或通过 `settings.operation`（partner 签名，通常不可行）。

**实测对比（为何音量可行、亮度不可行）**：

| 功能 | 走的组 | 在 public.groups？ | 结果 |
|---|---|---|---|
| 音量 `setVolume` | `audio.operation` | ✅ 是 | 成功 |
| 亮度 `setSystemSettings` | `settings` / `settings.operation` | ❌ 否 | Denied |

### 4.4 亮度键名（仅 root 场景参考）

电视是 OLED（G6），OLED 亮度键名为 `oledLight`，LCD 为 `backlight`。探测到电视型号参数含
`tv.model.defaultStdBacklight: 100`、`tv.model.toolType: "G6"`（见 `/tmp/var/log/dbg-log`）。
此键名信息**仅在具备 root 权限后才有意义**（普通 app 权限不足，即使键名正确也会被拒）。

### 4.5 已排除的路径

|---|---|

## 5. 所需 ACG 权限（实测后的最终版）

| 用途 | 服务 / 方法 | ACG 组 | 是否可行 |
|---|---|---|---|
| 设置音量 | `com.webos.audio/setVolume`、`getVolume` | `audio.operation` | ✅ 可行（在 public.groups） |
| 设置亮度 | `com.webos.settingsservice/setSystemSettings`（category=picture） | `settings`（all.groups）/ `settings.operation`（partner） | ❌ **不可行** |

实际写入 `appinfo.json` 的**有效**内容（只含真正生效的组）：

```json
"requiredACG": ["activity.operation", "database.operation", "network.query", "audio.operation"]
```

> **不要**声明 `settings` / `settings.operation`——实验证明它们对第三方 app 不生效，声明了也是 `Denied method call`。
> 依据 ACG 文档（`docs/官方文档/02-开发指南/应用基础/访问控制组ACG.md`）：应用内服务所用的 Luna API 也必须在**应用的** `appinfo.json` 里声明，服务本身没有独立 ACG。
> 但**前提是该组位于 `public.groups.json`**——这是本次探索最重要的教训（文档并未明说这一点）。

## 6. 时段调度可行性

项目后台服务 `wol_service.js` 是**常驻进程**（`keepResident()` + ActivityManager persist activity），
已有 `setInterval` 定时器（电源订阅重注册）。因此可基于它实现音量调度。

**已实现**：音量调度可用，且**支持记录用户各时段手动设置的值**（见开发者文档 §7.5）。

### 6.1 「记录用户设置值」的机制（订阅制，无轮询，24 小时目标）

**关键发现**：`com.webos.audio/getVolume` **支持订阅**（实测 `subscribe: true` 返回 `subscribed: true`）。
因此无需轮询——用户一调音量，服务立刻收到推送。

1. **订阅音量变化**：`service.subscribe(AUDIO_URI + '/getVolume', { subscribe: true })`；
   收到推送 → 若音量 ≠ 我们上次自动设置的值（`lastAppliedVolume`），视为用户手动调整 → 按**当前小时**记录目标值（`scheduleState.targets[h]`）并存入 DB8（kind `com.woltv.wakeonlan.volume:1`，字段 `hours`，长度 24 数组）。
2. **每小时边界定时**：`scheduleBoundaryCheck()` 算到下一个整点的毫秒数，`setTimeout` 精确触发一次应用（零轮询），触发后递归安排下一次（每天 24 次）。
3. **订阅断开由 `cancel` 事件驱动重连（不轮询）**：`webos-service` 的 `subscription.js`
   在收到 `subscribed:false` 或底层取消时触发 `cancel` 事件 → 指数退避重连（3s→60s）。**没有轮询存活检查**。
4. **启动**：`initTargets()` 初始化 24 个默认值 → 加载 DB8 → 应用 → 订阅 → 重算边界。

> **为何不用轮询**：早期版本每 30 秒 `getVolume` 轮询一次，频率偏高；改为订阅后，用户调节**实时**感知，
> 小时切换用**精确定时**触发，两者都不漏，也不浪费。24 个目标值按小时细分，比「白天/晚上两个值」更精确。

### 6.1.1 两个订阅的触发方式对比

应用内有两个常驻订阅，均为**事件驱动**（系统/服务在事件发生时主动推送，**不依赖轮询**）：

| 维度 | 电源订阅（tvpower） | 音量订阅（audio） |
|---|---|---|
| 订阅 URI | `tvpower/power/registerPreparePowerOn`、`registerPrepareResume` | `com.webos.audio/getVolume`（subscribe:true） |
| 触发源 | tvpowerd 系统推送 | audio 服务推送 |
| 触发时机 | 电视开机 / 从待机恢复 | 音量变化 |
| 触发后动作 | 应答 ack + 发魔术包唤醒电脑 | 记录当前小时音量目标值 + 应用 |
| 需要轮询吗 | ❌ 不需要（即时） | ❌ 不需要（即时） |
| 断线处理 | cancel → 5 秒重订阅 + 60 秒定时重注册 | cancel → 指数退避重连（3s→60s） |

> **关键**：两者都是订阅制、事件驱动、即时触发。这也解释了"电视开机后电脑秒开"（电源订阅即时）与"用户一调音量就记录"（音量订阅即时）。

### 6.2 订阅会不会断开？—— 官方文档依据（非假设）

有人质疑「订阅偶尔会被系统回收/断线」是凭空假设。**官方文档有明确依据**：

| 依据 | 出处 | 说明 |
|---|---|---|
| `resubscribe` 参数 | `docs/官方文档/03-API参考/webOSTV.js库/webOSTV.js的webOSAPI.md`（第 460 行） | 官方为 `webOS.service.request` 提供 `resubscribe`（"指示请求在发生失败后是否应重新订阅"）——**官方承认订阅可能失败、需要重订阅** |
| `subscribed:false` 终止订阅 | `docs/官方文档/03-API参考/无线与输入/BLEGATT蓝牙服务.md`（第 10 行） | "服务通过将 `subscribed` 设置为 false 来通知客户端它将不再发送任何后续订阅响应……当客户端收到 `subscribed` 的值为 false 时，**必须**调用 `LSCallCancel()` 或 `handle.cancel()`" |

**结论**：不是"系统定期回收"，而是**订阅可能失败、服务端可能主动终止**（官方预期内）。

### 6.3 本项目的处理方式：事件驱动重连（非轮询）

注意：`resubscribe` 是 **`webOSTV.js`（浏览器端）** 的参数；本项目后台用的是 **`webos-service`（Node 库）**，
**不支持 `resubscribe`**（已实测 grep 无结果）。它通过 `cancel` 事件感知订阅终止：

```js
// /lib/node_modules/webos-service/lib/subscription.js（电视上实读源码）
this.request.addListener("response", function(msg) {
    ...
    if (payload.subscribed === false) {
        self.request.cancel();
        self.emit("cancel", new Message(msg, handle));   // ← 订阅终止 → 触发 cancel
    }
    ...
});
this.request.addListener("cancel", function(msg) {
    self.emit("cancel", new Message(msg, handle));        // ← 底层取消 → 触发 cancel
});
```

因此本项目做法（**全部事件驱动，无轮询存活检查**）：

- `volumeSubscription.on('cancel')` → `scheduleVolumeRetry()` 指数退避重连（3s → 60s）。

> **为何不需要轮询**：断开时底层会**主动推送 cancel 事件**，服务据此自动重连，故轮询检查存活是多余的（曾有的 60 秒轮询已移除，心跳兜底也已移除）。

> **关键点**：用 `lastAppliedVolume` 区分「我们自动设的值」与「用户改的值」。
> `applySchedule(force)` 在启动/恢复/边界时以 force 调用，跳过记录、只重应用目标，避免把旧值误记为用户设置。
> **持久化**：`hours` 数组（24 元素）存 DB8，重启不丢。

**亮度**（调用会被拒，代码已移除）：普通 app 权限不足，见 §4.3。

## 7. 可复用的排查结论

- **源地址会变**：每次探测前先确认本机同网段 IP，不要照抄文档里的旧 IP。
- **权限错误分三种**：
  - `Access denied` —— 服务端权限组问题（如 prisoner 身份调 settingsservice）；
  - `Denied method call ... for category "/"` —— **该组不在 `public.groups.json`，普通 app 声明也无效**；
  - `Unknown method` —— 方法名错误。
- **判断 app 能否调某接口的正确方法**：先看方法属于哪个组（`api-permissions.d/*.api.json`），
  再确认**该组是否出现在 `groups.d/public.groups.json`**——只有那里的组第三方 app 声明才生效。
  `all.groups.json` 里 `public: true` 的组**不代表 app 能用**（本次踩坑点）。
- **内部方法靠 `api-permissions.d/*.api.json` 找**：先 `grep` 关键词（这里 `backlight`/`volume`），再看它落在哪个组。
